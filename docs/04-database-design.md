# 04 — Database Design

**Engine:** MySQL 8.0 · InnoDB · `utf8mb4` / `utf8mb4_0900_ai_ci`
**Access:** Prisma 5, schema split one file per bounded context under `prisma/schema/`

---

## 1. Conventions

| Rule | Detail |
|---|---|
| Table names | `snake_case`, plural (`unit_stages`) |
| Primary keys | `id CHAR(36)` holding **UUIDv7** — time-ordered for InnoDB insert locality, generatable offline by mobile clients |
| Tenant column | `company_id CHAR(36) NOT NULL` on every tenant-owned table |
| Money | `DECIMAL(18,4)` for amounts + `currency CHAR(3)`; never `FLOAT`/`DOUBLE` |
| Quantities | `DECIMAL(18,4)` + a `uom` enum column |
| Dimensions | Integer **millimetres** (`INT`) for geometry; `DECIMAL(12,4)` metres for user-facing areas |
| Percentages | `DECIMAL(5,2)`, 0.00–100.00 |
| Timestamps | `DATETIME(3)` stored **UTC**; display timezone resolved per company |
| Soft delete | `deleted_at DATETIME(3) NULL`, `deleted_by CHAR(36) NULL` — partial exclusion handled in the repository layer |
| Audit columns | `created_at`, `created_by`, `updated_at`, `updated_by` on every business table |
| Concurrency | `version INT UNSIGNED NOT NULL DEFAULT 0` on every aggregate-root table |
| Enums | MySQL `ENUM` only for values that are truly closed (`status`); everything tenant-extensible is a lookup table |
| Foreign keys | Declared and enforced; `ON DELETE RESTRICT` by default, `CASCADE` only within an aggregate |
| JSON | `JSON` columns permitted for genuinely schemaless payloads (geometry blobs, event payloads, AI responses) — **never** for anything filtered or sorted on |
| Index prefix | Every tenant-scoped index starts with `company_id` |

### 1.1 Why UUIDv7 and not auto-increment

Auto-increment leaks business volume across tenants (`GET /units/1841` tells a competitor how
many units exist), cannot be generated by an offline mobile client, and complicates future
sharding. UUIDv4 would fragment the InnoDB clustered index catastrophically at write volume.
UUIDv7 embeds a millisecond timestamp in the high bits, so inserts stay sequential while
remaining globally unique and offline-generatable. Stored as `CHAR(36)` for tooling readability;
`BINARY(16)` is a documented optimisation deferred until row counts justify it.

### 2.5 Spatial

`floor_plans` — `id`, `company_id`, `unit_id`, `name`, `version INT`,
`status ENUM(draft,active,archived)`, `scale_ratio`, `origin_x_mm`, `origin_y_mm`,

`geometry JSON` (denormalised full scene for fast load),
`thumbnail_object_key`, `locked_by_user_id`, `locked_at`, `lock_expires_at`, audit, `version`.

> **Dual storage.** The authoritative geometry lives in the normalised tables below (queryable,
> diffable, referenced by BOQ take-off). A denormalised `geometry JSON` snapshot is maintained

> JSON is a **cache**, rebuilt from the normalised rows; it is never the source of truth.

## 3. Indexing strategy

### 3.1 Principles

1. **Every tenant-scoped index begins with `company_id`.** This is both a correctness aid and
   the single most important performance decision in the schema.
2. **Index for the screen, not for the table.** Each index below exists because a specific,
   named query needs it.
3. **Covering indexes on hot list views** so the common list query never touches the clustered
   index rows.
4. **No index without a query; no query without an index.** A CI check runs `EXPLAIN` over the
   registered query catalogue and fails on any `type: ALL` scan over a table above a row
   threshold.

### 3.2 Critical indexes

| Query (screen) | Index |
|---|---|
| Project list with status filter | `projects (company_id, status, planned_end_date)` |
| Units in a project | `units (company_id, project_id, status)` |
| "My units" for a site engineer | `user_assignments (company_id, user_id, scope_type, scope_id)` |
| Units at risk (overdue) | `units (company_id, status, planned_end_date)` |
| Stage board for a unit | `unit_stages (company_id, unit_id, sequence)` |
| Overdue stages across the company | `unit_stages (company_id, status, planned_end_date)` |
| Photo gallery for a stage | `photos (company_id, unit_stage_id, category, taken_at)` |
| Material balance for a unit | `material_balances (company_id, unit_id, material_id)` |
| Stock ledger replay | `stock_movements (company_id, unit_id, material_id, occurred_at)` |
| Spend by supplier and period | `invoices (company_id, supplier_id, invoice_date)` |
| Audit trail for one record | `audit_logs (company_id, entity_type, entity_id, occurred_at)` |
| Material catalogue search | FULLTEXT `materials (name_en, name_ar, sku)` |
| Client search | FULLTEXT `clients (name_en, name_ar)` |
| Outbox relay poll | `outbox_events (published_at, available_at)` |

### 3.3 Full-text search

MySQL FULLTEXT with `ngram` parser for Arabic (the default parser's word boundaries do not
handle Arabic morphology well; a 2-gram index gives acceptable recall). Minimum token length is
tuned to 2. Search moves to OpenSearch at Stage 3 — see [17 — Scalability](17-scalability.md).

## 4. Audit strategy

Three complementary mechanisms, each with a distinct purpose:

| Mechanism | Covers | Retention |
|---|---|---|
| `audit_logs` | Who changed what, before/after, on **every** business entity | 7 years (regulatory) |
| Domain event log (`outbox_events` + `stage_transitions`) | Business-meaningful facts, replayable | 2 years hot, then archived |
| `stock_movements` | Immutable material ledger | Forever |

Audit records are written **inside the same transaction** as the change, from a repository
decorator — not from controllers, and not asynchronously. An async audit write that fails leaves
a change with no record, which defeats the purpose.

**Auto-captured fields:** actor, timestamp, IP, user agent, request ID, source (web/mobile/api),
entity type + ID + human label, changed fields with before/after values.
**Reason required** for: stage rejection, cost override, BOQ line override, quantity adjustment,
hard delete, permission change, and project hold.

## 6. Data integrity rules enforced in the database

| Rule | Mechanism |
|---|---|
| Unit number unique per project | `UNIQUE (company_id, project_id, unit_number)` |
| Only one active workflow per unit | `UNIQUE (company_id, unit_id)` on `unit_workflows` where active |
| BOQ version unique per unit | `UNIQUE (company_id, unit_id, version)` |
| One balance row per material/stage | `UNIQUE (company_id, unit_id, unit_stage_id, material_id)` |
| Idempotent offline writes | `UNIQUE (company_id, client_event_id)` on `stock_movements`, `stage_transitions` |
| Referential integrity | `FOREIGN KEY … ON DELETE RESTRICT` (CASCADE only inside an aggregate) |
| Progress bounds | `CHECK (progress_percentage BETWEEN 0 AND 100)` |
| Non-negative quantities | `CHECK (quantity >= 0)` — direction is a separate column |
| Date sanity | `CHECK (planned_end_date >= planned_start_date)` |

Invariants that span rows or aggregates (`Σ allocations = invoice total`, `remaining ≥ 0`) are
enforced in the domain layer inside a transaction, because MySQL cannot express them
declaratively — and are additionally verified by a nightly reconciliation job that alerts on
drift rather than silently correcting it.

## 7. Migration policy

- Every change ships as a Prisma migration, reviewed like code, with a written rollback plan.
- **Expand → migrate → contract** for breaking changes: add the new column, dual-write,
  backfill, switch reads, remove the old column in a later release. No release ever requires
  simultaneous app + schema cutover.
- No destructive change (drop column/table, narrow type) in the same release that stops writing
  to it. Minimum one release gap.
- Backfills of > 100 k rows run as chunked background jobs, never inside a migration.
- Migrations are tested against a restored production-shaped dataset in staging before release.
- For dedicated-database tenants, the runner iterates registered databases and records progress
  in `tenant_migration_state`, so a failure mid-rollout is resumable rather than restart-only.

## 8. Backup & recovery

| Item | Policy |
|---|---|
| Full backup | Nightly, encrypted, off-site, 30-day retention |
| Incremental | Binlog shipping, 15-minute RPO |
| Point-in-time recovery | Any moment in the last 7 days |
| Object storage | Versioning on, cross-region replication, lifecycle to cold tier at 180 days |
| Restore testing | Quarterly full restore drill into an isolated environment; the result is recorded |
| Per-tenant export | On-demand: full data export as SQL + a media archive, generated by a worker |
| Tenant deletion | Soft-suspend 30 days → anonymise → purge; every step audited |
